# 从需求到发布的仓库管理流程

状态：初版交付中。长期以 GitHub `GoesM/voice_changer` 管理源码、Issue、CI 和 Releases；根目录 AGENTS.md 固化约束。v0.1.0 是技术预览，正式产品验收仍需后续完成。

## 1. 阶段与门禁

| 阶段 | 主要产物 | 进入下一阶段的条件 |
| --- | --- | --- |
| 需求发现 | PRD、待确认问题、使用场景 | 用户确认首发范围、效果、应用、硬件、安装条件与验收口径 |
| 技术验证 | PoC、测量报告、方案 ADR | 链路、效果、性能和分发路径有证据；无法达标项回到需求决策 |
| 设计与拆分 | 模块边界、接口、任务、验收映射 | 每个任务关联需求 ID，依赖与完成条件明确 |
| 开发 | 小步变更、代码审查、自动检查 | 功能与异常路径通过适当测试，变更可复现 |
| 集成验收 | 兼容矩阵、性能报告、安装包 | 全部首发 P0 和质量门禁通过，无阻断缺陷 |
| 试用与发布 | 发布说明、安装指引、恢复方案 | 试用问题闭环，依赖和模型分发依据齐备，安装包验证通过 |
| 维护 | 缺陷记录、版本回归、需求变更 | 每次修复可追踪影响范围，新增平台/模型重跑相关验证 |

## 2. 文档和代码组织

当前已建立 README.md、docs/product/PRD.md、docs/engineering/FEASIBILITY.md 和本流程。

开发阶段按需要增加：docs/decisions/（ADR）、docs/validation/（验收证据）、apps/desktop/（UI）、engine/（音频处理）、platform/（平台适配）、tests/、packaging/。未定技术栈之前不生成占位工程。

## 3. 需求追踪与任务规则

追踪链：需求 ID → Issue/本地任务 → PR/变更 → 测试记录 → 发布版本。

任务模板：标题、关联 FR/NFR、用户问题、范围、非范围、依赖、实现说明、验收步骤、证据、风险/恢复方式、负责人、状态。

任务状态：Backlog → Ready → In progress → Review → Verified → Done；Blocked 要记录阻塞原因和解除条件。无远程平台时用本地文档维护同样字段。

Ready：需求明确、验收可执行、依赖已知。Done：代码审查、相关测试、文档和追踪完成；不能把“代码写完”当作“需求验收通过”。

## 4. Git 和代码审查建议

建立 Git 后采用 main + 短生命周期功能分支；一个变更聚焦一个可审查目标。合并前检查构建、静态分析和与修改有关的测试。涉及音频线程、跨进程通信、驱动和故障策略的变化必须专项审查。

PR 描述包括问题、最终行为、关联需求、验证证据、已知限制及恢复方式。驱动签名凭据、密钥、原始私人录音和大模型权重不提交到源码仓库。模型通过版本化清单记录来源、哈希与获取方式。

ADR 记录：背景、候选方案、选择依据、后果、状态及日期。首批决策：首发平台、虚拟设备路线、处理引擎/模型、故障策略、安装分发方案。

## 5. 测试与发布

自动检查覆盖有意义的算法/队列行为、接口集成、构建与打包；真实音频设备、端到端录音、系统安装与睡眠恢复需要真实环境验证，不能由模拟测试代替。

版本采用可追踪的版本号和变更日志。每个发布保存代码版本、依赖锁定、模型/驱动版本、构建步骤、安装包校验值、测试矩阵、已知问题与恢复步骤。驱动更新失败和卸载恢复必须有独立验收证据。
